# ADR-005 · P2 多人统一结算与招式配置

负责人已验收 P1 并启动 P2。新增公开模块 `ofe_combat_core::arena`。P1 的 Duel 包装同一套动作推进、深度判定、碰撞和命中结算，保留已有构造、错误、事件顺序、状态枚举和观测时序。P0 ABI v1 和既有 OFC 1.0 均保持原契约。

## Rust 边界

复用 `duel::{AttackConfig, FighterConfig, LaneConfig, Controls, Fighter, Event, DuelError}` 与根模块的 EntityId、Position。下列结构字段公开；输入和配置按值构造。ID 与队伍由配置显式分配，fighter.id 唯一非零。阵容允许 2 至 4 个实体，至少两个不同队伍，友方免伤；2V2 与 FFA 分别由 [1,1,2,2] 与互异队号组成。

```rust
Arena::new(config: ArenaConfig) -> Result<Arena, DuelError>
Arena::step(&mut self, frame: u64, inputs: &[Command]) -> Result<(), DuelError>
Arena::frame(&self) -> u64
Arena::fighters(&self) -> &[ArenaFighter]
Arena::events(&self) -> &[ArenaEvent]
Arena::projectiles(&self) -> &[Projectile]
```

| 类型 | 字段/变体 |
|---|---|
| ArenaConfig | fighters: Vec<CombatantConfig>, lane: LaneConfig |
| CombatantConfig | id: EntityId, team: u32, base: FighterConfig, moves: Vec<MoveConfig>, dash_speed: i32, dash_ticks: u32, max_energy: i32, initial_energy: i32 |
| MoveConfig | base: AttackConfig, kind: MoveKind, hitstop: u32, windows: Vec<Window>, cancels: Vec<Cancel>, armor: u32, invulnerability: u32, energy_cost: i32 |
| MoveKind | Strike, Throw, Projectile { speed: i32, lifetime: u32 }, Super |
| Window | start: u32, end: u32（包含两端） |
| Cancel | window: Window, into: usize |
| Command | id: EntityId, controls: Controls, dash: bool, move_index: Option<usize> |
| ArenaFighter | fighter: Fighter, team: u32, energy: i32, combo: u32, hitstop: u32, move_index: Option<usize>, dashing: bool |
| Projectile | id: u64, owner: EntityId, position: Position |
| ArenaEvent | Base(Event), Started { id: EntityId, move_index: usize }, Cancelled { id: EntityId, from: usize, into: usize }, Dashed { id: EntityId }, Armored { attacker: EntityId, target: EntityId }, ProjectileSpawned { id: u64, owner: EntityId } |

P1 FighterConfig.attack 必须等于 moves[0].base，避免同一角色的普通攻击有两份冲突配置。Dash 以正 dash_speed 单位移动 dash_ticks 帧，方向取 axis 或当前 facing。move_index 指定动作，controls.attack 默认为索引 0。忽略不能执行的合法请求（如能量不足）；未知/重复 ID、非法轴或无效索引拒绝整帧。省略实体输入即中立。配置顺序与输入顺序均不影响结果；按实体 ID 升序输出。面对最近活跃敌方，按水平距离再按 ID 确定目标。P1 两人情形保留原有朝向与动作优先级。

## 时间、碰撞与数据边界

- 整个动作从年龄 0 开始。windows 为空时使用 base 的单个有效区间；显式多段 windows 使用相对动作开始的帧号，须按升序排列、互不重叠且位于有效区间。每个有效窗口对每个敌人至多结算一次。取消窗口也是绝对动作年龄；发生过该动作的有效命中且当前处于窗口时，可转入指定的另一个招式并支付新动作成本。按来源与目标明确记录取消。
- 投技在有效窗口内沿用矩形、双线和敌对判定，绕过格挡及护甲。Super 采用招式配置的消耗，在动作启动时扣费，不得消耗成负数。invulnerability 为从动作年龄 0 开始的无敌帧数，免疫接触；armor 为该动作可承受的命中次数，消耗后受伤但维持动作。生命归零优先进入 Ko。
- 投射物在动作首个有效帧生成一个独立实例，继承所有者位置、深度、朝向和招式规则；生成帧按原点判定，以后每活动帧前进 speed，含生成帧存活 lifetime 帧。每个投射物对每个敌人最多命中一次。投射物携带来源招式上下文，所有者动作结束后仍能结算。
- hitstop 在发生命中或格挡之后冻结相应攻击者和目标的后续指定帧；冻结期间动作年龄、硬直、位移暂停，模拟 frame 仍推进。多个同帧来源取最大停顿和硬直。对同一目标连续命中以每个攻击者/目标的硬直连续性跟踪连招；ArenaFighter.combo 为该攻击者仍有效连段中的最大计数，脱离连段后归零。格挡不增加计数。
- 帧内流程为规范化输入 → 同时推进动作与投射物 → 收集候选接触 → 按稳定的 (攻击者、目标、实例、窗口) 顺序分配可消耗护甲等资源 → 聚合伤害、位移、硬直 → 一次提交。已登记的同帧互击在双方同时 KO 时均有效。任意溢出回滚整帧。基础视图用 P1 的 Attack 表示投技、Super 与投射物施放，用 Walk 表示 Dash；move_index、dashing、Started 等细化 P2 观测。
- 验证非负能量与消耗、初始能量不高于上限、正 dash 参数、正投射物速度/寿命、有效时序和取消目标。仅验证后的外部数据可进入模拟。角色的命中、恢复、硬直、hitstop、armor、invulnerability、energy_cost、cancel_windows、lane_rule 从 OFC moves 读取。角色属性的 max_energy 来自 attributes；initial_energy 与位移参数属于场景。
- 辅助配置使用独立 `move_profile.json`，顶层字段 `format="OFE_MOVE_PROFILE"`、`format_version="1.0"`、`moves`。每项包含 `id`（匹配 OFC move.id）、`kind`（strike/throw/projectile/super）、`windows`（start,end 数组）、`cancel_into`（目标 OFC move.id 数组）；projectile 项另需 `speed,lifetime`。cancel_into 对应来源 OFC 的每个 cancel_window（笛卡尔组合）。同一角色 moves 以 manifest.moves 顺序稳定索引；必须检查配置缺失、未知 ID、重复 ID、投射物参数和窗口边界。P1 不需要辅助文件。P2 的模拟器从场景明确指定本地配置路径，OFC 1.0 manifest 无需新增字段。P3 再决定原生整合策略。
